# Managed runtime permissions

The managed companion uses the existing signed runtime endpoint and unchanged MCP relay. It retains one original JSON-RPC message, exact runtime authority, endpoint, engine, relay, socket binding and original admission verifier throughout the call. Node's private asynchronous execution context binds every relay callback, including read and session tools, to its original request. A delayed SDK callback cannot adopt a newer matching request. A tool callback can claim its original message only once. It cannot substitute another tool or arguments, create another permission for the same call, or retain authority after a disconnect or replacement runtime.

The existing browser policy remains the first gate. Hard denials, credential actions, text entry, key presses, scripting, coordinate control and unsupported writes cannot obtain an approval through this lane. A policy request can use only the backend's supported navigation, click, dialog, selection, upload and PDF method set. PDF retains its existing read classification, so this change adds no PDF prompt. Background profile consent does not grant a site permission. Read tools keep their existing policy behavior.

For a supported request, `AgentRuntimePermissionRunner` captures the selected native Page object, its full URL and navigation, close and crash events. The original page, selection, URL and event generation must remain unchanged through every asynchronous permission step and immediately before consumption and execution. Even a navigation away and back invalidates the held action. The companion also rechecks the original frame bytes, endpoint, full runtime and binding authority, socket, account scope and original cancellation capability. A changed page needs a new deliberate action rather than an automatic retry.

## Bounded owner review

The client creates one gate through the configured HOAI origin with a fresh pairing capability and endpoint signature. The permission document contains a fixed action kind, canonical origin, complete authority and hash of the original stored request. It contains no page text, tool arguments, password, OTP or private key. The original browser RPC already belongs to the separate authenticated runtime transport.

The person using the agent opens Agent machine to review a pending request in the native HOAI window. Discovery and decisions are scoped to that recipient and assistant. The client trusts HOAI's authenticated response for the person's answer. Non-navigation origins are reported by the agent machine, and the native review states that HOAI has not independently verified the page URL.

The agent performs at most 60 signed reads, separated by a delay of up to one second, within the earlier of 60 seconds or the original RPC deadline. This is an in-flight command wait, not background discovery or a recurring task. Each HTTP request remains bounded by the standalone client's timeout and physical reservation. An unanswered, denied, expired, changed or historically consumed gate does not execute. The owner can explicitly review again, but the original agent request is never sent again automatically.

A lost creation acknowledgement retains an opaque handle. Read-only reconciliation starts only after that original HTTP work physically drains. An `allow_once` answer requires one fresh successful consume POST for that exact handle before the engine runs. An unknown consume acknowledgement is refusal: it is never resent and a later readback saying consumed cannot authorize execution.

## Physical lifetime

The companion's command reservation covers the permission wait, HTTP cleanup and engine operation. A relay response timeout cannot settle the native command promise early. Disconnect, close and revocation invalidate held admission; a late answer cannot start an action.

The portable extras store retains a separate lifetime proof from creation admission. New creation checks still reject shutdown before and after every factory await. The stored extras proof remains valid for the exact original runtime during normal checkpoint shutdown, while private preparation identity, full authority, exact acting scope, disposal and revocation still fence it. Reusing the creation-only closing check would prevent saved logins and preferences from being captured during a normal daemon stop.

Revocation starts native browser disposal independently of waiting permission HTTP. The disposal result then waits for the original command work to settle. Page listener installation is transactional and cleanup attempts every installed or attempted listener independently. The runner's `assertCleanupConfirmed()` is a private positive cleanup receipt after its operation settles. A failed HTTP or listener cleanup remains in the command set and a private companion latch prevents new admission even if public bookkeeping is replaced. The shared runner also refuses any further permission run for every profile using it after uncertain cleanup; it checks that latch before any operation. The source cannot claim a positive command drain or completed local disposal in that state. A routing release is not a physical drain receipt, and a browser-close RPC must not await its own routing promise.

## Security and evidence limits

Passwords, OTPs and arbitrary scripts receive no new automatic authority. Native browser use, encrypted per-agent login storage and any approved profile transfer remain separate features. This permission change does not weaken their save or encryption boundaries.

HOAI is trusted to authorize the human decision and return it honestly. TLS and endpoint possession proofs prevent another ordinary account, unpaired endpoint or stale request from borrowing this approval; they do not defend against a compromised HOAI server falsifying the decision. The approved agent operator and OS account can inspect the browser and plaintext while the profile is in use. A modified agent process can bypass its own local checks, so approving its machine requires trusting that operator.

The focused tests use the actual runtime endpoint state machine and unchanged `RelaySessions`, with explicit signed-dispatch, pairing and human-answer fixtures. One case uses the actual permission HTTP client with a late streaming response and held cancellation, proving that native disposal starts while the HTTP body remains reserved and no late action executes. These are deterministic composition tests. They do not by themselves prove a real desktop native decision, production delivery, two-machine networking or arbitrary website compatibility.

A successful normal browser-close command changes the writer to stopped and disposes its active endpoint. The backend's existing stopped-runtime observer retires original physical RPCs with an uncertain caller outcome, and the endpoint also rejects returning data under a disposed active authority. Consequently the close RPC can report uncertainty even when the separate checkpoint commit succeeded. This change preserves that conservative protocol behavior. The committed profile state is the close proof; the agent must inspect that state rather than retry the close, invent active authority, or reopen the browser.
