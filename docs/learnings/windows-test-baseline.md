# The Windows test baseline is green now, and a CI leg keeps it there

**Date:** 2026-08-25, rewritten 2026-10-04

**Context:** Until 2026-10-04 the suite had only ever run on Linux (CI) and macOS. On a Windows box pristine `main` failed a fixed set of tests that this note used to list name by name (13 node + 1 bun in August, 30 + 1 by October on an LF clone, 41 + 3 on a default CRLF clone), and the advice was to clone with `core.autocrlf=false`, save the failing block as a baseline, and call a run green when its failing block matched that baseline name for name. That advice fixed one machine and hid three real Windows bugs inside the "expected" list. It is withdrawn.

**Gotcha / Pattern:** Every one of those failures has a cause, and none of them is "the box". Triaged one by one (`fix/windows-suite`):

- **Real Windows bugs, fixed in the product.** The export pack's symlink gate checked containment with a hardcoded `/` against a backslash realpath, so every Full handoff from a Windows agent failed PATH_ESCAPE. `bgos-claim` left the API key in `.mcp.json` under the folder's inherited ACL while printing "chmod 600". The daemon stopped its browser host with `kill('SIGTERM')`, which is TerminateProcess on Windows, so Chrome was cut off on every stop (see [a-windows-child-dies-with-its-parent](a-windows-child-dies-with-its-parent.md)).
- **Tests that assumed POSIX, fixed in the test without weakening it.** Path fixtures written as POSIX literals against a lib that joins with the host separator; RegExps built from a Windows path; 0600 mode asserts (NTFS shows only the read-only bit, so the Windows half now asserts "never read-only", which can still fail); `chmod 0500` on a folder as fault injection (NTFS and root both ignore it; a directory or file in the way fails everywhere); a bare `bash`, which on Windows is the WSL launcher and cannot open `E:\...`; `pgrep`, which Windows does not have; a 400 ms budget shorter than a cold node start under load.
- **Line endings.** A Windows install is a git clone made with the user's `core.autocrlf=true`, so 349 files reached Windows users as CRLF. `.gitattributes` now pins every text file LF (batch files CRLF), so no clone needs a setting, and `test/line-endings.test.ts` pins the rule on Linux CI.
- **Environment, documented in the README ("Running the tests"), not here.** Git for Windows for the bash tests (found next to `git`, never the WSL launcher); no `expect` on Windows, so the run.expect tests skip there with the reason; Developer Mode for the two FILE symlink cases, which skip with the reason without it.

**How to apply next time:** a Windows red is a bug until shown otherwise; never file it under "the box". Ask which side is wrong before touching the assertion: trace what the REAL caller passes (homedir() is `C:\Users\name`, realpath returns backslashes, `process.platform` is win32), because rewriting the matcher can hide a user-facing bug. Judge a Windows run by `npm test` exiting 0, not by comparing failing blocks.

**Regression guard:** the `test (windows)` job in `.github/workflows/tests.yml` runs `npm test` and `bun run build` on `windows-latest` for every pull request and every push to main, with the runner's own git config (so a CRLF regression is a red), `HOAI_REQUIRE_BASH=1`, and the real Chrome end to end. `test/line-endings.test.ts` guards the `.gitattributes` rule on both legs.
