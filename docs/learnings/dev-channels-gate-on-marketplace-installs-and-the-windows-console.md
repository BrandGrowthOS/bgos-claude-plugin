# The dev-channels gate fires on marketplace launches too, no settings key silences it, and on Windows it is accepted from the console buffer

**Date:** 2026-08-25

**Context:** Unattended relaunches (update restarts, watcher restarts) on Windows, where there is no `expect`. Claude Code 2.1.241 prints `WARNING: Loading development channels ...` with a menu whose default (Enter with nothing selected, or a blind Enter at the wrong moment) is "no, exit".

**Gotcha / Pattern:**
- The gate shows for MARKETPLACE installs as well as clones whenever `--dangerously-load-development-channels` is on the command line, and it is on the line for marketplace launches too (`plugin:hoai@hoai` alone loads tools and delivers nothing; see the BGOS learning `claude-channels-flag-loads-but-never-delivers`). The settings key `dangerouslyLoadDevelopmentChannels` does not suppress it on this version; `skipDangerousModePermissionPrompt` only covers the permissions prompt.
- The Windows helper (`bin/win32-accept-dev-channels.ps1`) attaches to the launcher's console (`AttachConsole(pid)`), reads the LIVE screen with `ReadConsoleOutputCharacter` over a `CONOUT$` handle reopened on every poll (the TUI switches to the alternate screen buffer; a handle opened once keeps reading the old one), and sends Enter through `WriteConsoleInput` only after the gate marker text is on screen. `0xC0000000` must be cast to `[uint32]` in PowerShell 5.1 or the handle open fails silently.
- Spawn the helper with `detached: false`. Detached, it exits 0 within a second having attached to nothing, and the log says "accepted" for a gate it never saw.
- (2026-10-16, agent 888, board row d806c69f) A log line can vanish while the helper carries on. PowerShell 5.1's `Add-Content` refuses a file that ANY other process has open for reading, even one that shares everything, and it is a NON-terminating error: `try { Add-Content ... } catch {}` neither catches it nor knows. 888's cold start logged `start`, then `accepted`, no `attached`; the real helper reproduces exactly that, with Add-Content's refusal text between the two lines (its stderr is the same log), whenever one reader holds the log while `attached` is written. Append through a FileStream opened append-only (`FileSystemRights.AppendData`) that shares `ReadWrite, Delete`, which no reader refuses (`[IO.File]::AppendAllText` shares read only, and so collides with hoai's own append handle), and let the exit code carry what the log still could not take: the helper now exits 0 only with both `attached` and `accepted` on record, else 6, and an unattended hoai relaunches claude for a 6. `accepted` still only proves an Enter reached the console input, so hoai also relaunches, once, a launch whose channel beacon (`channel-beacon.json`) is silent 3 minutes in.

**How to apply next time:** Treat "the prompt was accepted" as something you prove from the screen, not from a return code: log `start / attached / accepted` with timestamps, and in an E2E read the console buffer (a 30-line Python ctypes reader does it) to see what the model is actually looking at. Never send Enter on a timer. A PASS check on the helper's log needs `attached` AND `accepted` from the same `pid=`, never `accepted` alone (`docs/evidence/2026-10-16-gate-attach/gate-proof.ps1`); the proof that the agent is up is its daemon's boot and channel beacon after that.

**Regression guard:** `test/hoai-supervise.test.ts` (`win32 gate helper source: only ever presses Enter after the gate marker is on screen, never blindly`; `win32GateHelperArgs`; the helper is spawned non-detached with a log file). `test/hoai-core.gate-attach.test.ts` (exit 6 relaunches, the heartbeat check) and `test/win32-gate-helper.console.test.ts` (the real helper on a fake console: exit 0 with all three lines, exit 6 with the log held open). Live: `~/.bgos-agent/logs/win32-gate-helper.log` showed `attached` then `accepted` within ~1.1s on every relaunch of the E2E.
