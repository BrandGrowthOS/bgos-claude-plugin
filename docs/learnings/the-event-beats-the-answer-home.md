# The event beats the answer home, so a stamp taken after the response is a stamp taken too late

**Date:** 2026-09-20

**Context:** Stage 5 of the Mission program made the daemon listen for mission events so the owner's Set aside, Mark done, Pause and Resume reach the model. To stop the daemon narrating the model's OWN writes back to it, each mission tool stamped the mission it had just written and the listener skipped a frame carrying that stamp. The stamp was taken from the tool RESULT, on the line after the await.

**Gotcha / Pattern:** The backend emits the WebSocket frame from inside the same transaction it answers the HTTP call from, so the frame regularly arrives at the socket handler while the tool is still awaiting its response. At that moment nothing is stamped, and the frame reads as somebody else's write. The visible failure is the worst one available here: the agent ticks the last open mini goal, the backend auto completes the mission and emits `mission_completed` with no `cleared_by` (only an agent can tick, so the backend had nothing to say), the frame wins the race, and the model is told that its owner marked done the mission it had just finished itself, with an instruction to stand down and post a line saying where it stopped. Everything about that report is honest and every word of it is wrong.

Three things the fix depends on, none of them obvious:

1. **A stamp has to exist before the thing it is a stamp for.** The pending stamp is taken by mission id BEFORE the request leaves, which is the only moment guaranteed to precede the frame. The after the fact stamp (mission id plus `updatedAt`) is kept, because it is what covers a frame delivered LATE, a reconnect catch up being the real case. Two stamps, two races, neither one redundant.
2. **A pending stamp is spent, not held.** It answers for ONE frame and is then gone, or the owner's next change to the same mission would be swallowed by a stamp left lying around from an earlier write.
3. **Only a frame that could be narrated may spend it.** One tool call can emit two frames: a tick that closes the last goal emits `mission_ticked` AND `mission_completed`. `mission_ticked` is never narrated, so if it spent the stamp the completion behind it would look like the owner's own Mark done and the defect would come back wearing a different frame.

**How to apply next time:** Whenever a local write and a server pushed event describe the same fact, write down which one can arrive first and assume it will. "Do the thing, then remember you did it" is only safe when nothing can observe the thing between the two lines; a socket handler in the same process can. Take the mark before the call, key it on something you already know at that point (here the mission id, not the response body), bound it, and spend it once. And put the whole decision in a pure module so the race is a unit test with two lines in a chosen order rather than a timing experiment nobody reruns.

**Regression guard:** `test/mission-events.test.ts` (the self write ledger block: `a write stamped only AFTER the response loses the race the socket wins`, `one pending stamp answers for one frame, so the owner is still heard afterwards`, `a tick riding the same call does not spend the stamp the completion needs`, `the after the fact stamp still covers a frame that arrives late`, and the bound). `test/mission-ws-wiring.test.ts` (`the writing tools stamp the mission BEFORE the request, not after the answer`, which fails if the stamp moves back below the await, and `the mission listener asks the ledger, so both stamps are consulted on one line`).
