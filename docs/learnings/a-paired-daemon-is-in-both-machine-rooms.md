# A paired daemon is in BOTH machine rooms, so "it cannot hear mission events" was wrong and the dedupe is not optional

**Date:** 2026-09-20

**Context:** Stage 5 of the Mission program had to make the owner's Set aside, Mark done, Pause and Resume reach the agent. The program map and the design vocabulary doc both stated that a Claude Code plugin socket joins only `assistant:<id>`, that the backend emits mission events to `user:<id>` and `pairing:<id>`, and therefore that this channel could not hear a mission event at all without new backend fan out. The planned backend change was sized against that belief.

**Gotcha / Pattern:** That describes the LEGACY X-API-Key install only. The modern plugin pairs with a one time code (`lib/agent-credentials.ts`: `wsAuthOptions` sends `{ query: { pairingToken } }` for `pairing`, `{ auth: { apiKey, assistantId } }` for `apikey`, and `missingCredsMessage` calls the API key path "the legacy manual setup"). On the backend the pairing handshake joins `pairing:<id>` AND `assistant:<id>`, both. So the fleet was ALREADY being sent every mission event and simply had no listener. Two consequences, and the second is the dangerous one:

1. The backend work was narrower than the map claimed: an `assistant:<id>` copy is needed only for the pairingless population, not for everyone.
2. **A paired daemon sits in two rooms that both carry mission traffic.** Whether it is told once or twice depends on one `if` in the gateway. socket.io dedupes per socket within ONE `.to(rooms).emit(...)`, and not across two emit calls, so an edit that turns that `if` into two unconditional emits double tells the model that its mission died. A double rendered card is cosmetic; telling a model twice that its goal is dead, in its context window, is not.

**How to apply next time:** Do not take "which rooms does this client join" from a map, a design doc or a comment. Read the handshake in `websocket.gateway.ts` and the auth options the client actually sends, and read them per AUTH MODE, because two populations of the same plugin can join different rooms. Then assume the room membership will change under you: the listener carries its own bounded dedupe keyed on the frame, the mission id and `updatedAt` (a per-write key, because the backend bumps `updated_at` on every write), so correctness does not depend on a backend `if` that a future edit can flip. The same reasoning produced the self write stamp: the agent's own create, tick and complete all come back as events, and an unstamped handler narrates the model's own write back to it on every tick, forever.

**Regression guard:** `test/mission-events.test.ts` (the parse, the narrated set, the self authored and already seen drops, and both key helpers: two copies of one event share a key, two writes to one mission do not, and the self write key carries no frame so a create that also emits an abandon is stamped once). `test/mission-ws-wiring.test.ts` (eight literal registrations, the drain guard on each, no socket registration anywhere takes a variable frame name, and a self write stamp inside each of the three mission tool cases). `test/pairing-lock-standdown.test.ts` counts the eight new frames into `PAIRING_FRAMES`, so a ninth mission frame added without the stand down gate fails the suite.
