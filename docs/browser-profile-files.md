# Explicit files for one managed browser runtime

This main-process foundation uses the separate signed and encrypted HOAI file channel. It is not yet composed into Companion in this commit. No tool accepts a desktop or agent source path. Ordinary managed downloads remain denied, and files are not included in sign-in checkpoints or synchronized directories.

AgentProfileFiles is created with one exact full active authority, its own endpoint private key, one fixed paired ProfileFileClient, a trusted private directory, a fresh locally reviewed peer-identity loader and a synchronous original-runtime checker. Every action rechecks that original runtime and optional original RPC cancellation. Discovery uses version 2 of the existing pending-file route and may learn current grant versions only for the one to four locally reviewed human public identities. A response cannot introduce a new trusted identity.

hoai_browser_files returns safe metadata and opaque runtime file tokens. It also lists opaque recipient tokens with full public fingerprints. Multiple recipient devices require explicit token selection. Pending offered files carry no website input authority. An incoming upload must name exactly one hoai-file token in the original browser_file_upload paths argument. The existing website permission request hashes and consumes that unchanged original request. Only its execution callback can read the original file status, claim ciphertext once, decrypt it and materialize the original basename privately. That callback rechecks the exact selected page object, full URL, origin and navigation/close/crash history across every await before invoking the unchanged engine with a generated local path. Cancellation, another page, changed arguments or an uncertain consumed delivery cannot retry the upload.

Browser screenshots and PDF saves may mint hoai-artifact tokens only after an actual successful unchanged engine call writes into an exclusively created UUID child directory. A caller filename can be only a validated basename; the wrapper supplies the generated private path. Tool text, arbitrary paths and agent-supplied file links never become inventory. The token result includes basename, byte count and expiry; host filesystem paths are not returned. The actual read-only PDF policy classification is unchanged by this foundation.

hoai_browser_send_file accepts only an owned artifact token and optional recipient token. The source is revalidated and read with no-follow/inode/size checks, sealed to the exact reviewed recipient and erased from plaintext memory. The original opaque offer handle is retained before the first possible POST. The first call creates an offer only. The recipient must approve that individual file in the native HOAI UI. A later explicit tool call may read that choice and upload the encrypted payload once. No automatic polling or consent inference occurs. Unknown creation, upload or claim outcomes become read-only and never repeat a mutation. A grant or active-authority change invalidates the operation rather than retargeting it.

AgentProfileFileArea accepts only Linux with positive current UID and owner-only directory mode proof. It refuses permissive existing directories, symlink ancestry, path normalization changes and a different realpath. It never chmods or adopts a linked directory. It retains original ancestry inode proofs and verifies them before later use. Its returned directory verifier is an ownership-only capability: it deliberately remains usable for independent physical cleanup after runtime revocation and grants no browser or network authority. Shared staging performs its separate current-context checks before and after that read-only verifier. Protection from a hostile process with the same OS user is not claimed.

Each runtime admits one file operation; four actual runner operations are admitted process-wide. These slots remain held through actual relay response, owned buffer and cleanup settlement. Source artifact inventory is four per runtime, sixteen process-wide, at most 25 MiB each and 400 MiB total; artifacts expire after ten minutes. Incoming and outgoing metadata inventories are bounded at sixteen each, with at most four retained outgoing encrypted payloads per runtime. The shared client additionally has its one physical HTTP slot, 64 bounded retained handles and positive body cleanup. Source files and partial materializations are removed only with positive owned-directory/inode proofs. Independent listener, file and response cleanup failures privately latch uncertainty and retain their physical reservation. Disposal aborts new admission immediately and begins client, private staging and artifact revocation independently before waiting for actual work. A normal command cancellation is not itself a failed physical cleanup receipt.

The focused tests use actual shared encryption, source signatures, immutable human consent, ProfileFileClient streams, one-use claims, shared staging and real temporary filesystem reads/writes. HOAI responses, native decisions and Linux UID/mode receipts are synthetic in these Windows unit tests. Actual Linux privacy, native approval and two-machine file delivery require separate composed qualification. Existing browser engine, bridge, relay and production records are unchanged by this foundation.
